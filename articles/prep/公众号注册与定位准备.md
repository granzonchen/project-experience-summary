## 十、远期储备：projects-old 的"退役终点站"规划（2026-09-06 立）

> 背景：projects-old 三批瘦身（10.6→4.0GB）+ 全量脱敏 + Gitee 双备份后，4.0GB 的"归档地"本身需要一个终态设计。以下规划待逐项拍板。

### 阶段 R1 · 终态架构定版（1 次会话）
- 目标形态：`projects-old/` 只留**两层**——①治理文档区（5 份 .md 治理记录）；②压缩归档区（`_archive 化`：每个项目一个 7z + SHA256 清单，与 `D:\projects\_archive\` 合并管理）
- 原则：项目源码目录不再以"散装目录"形态存在——要么进 7z（有 Gitee 备份的项目可低优先级），要么保持现状并在清单标注"保持原样"
- 产出：《projects-old 终态方案》一份，含逐项目处置表（压缩/保持/删除三选一）+ 预期体积

### 阶段 R2 · 项目级压缩归档（1~2 次会话，回收站纪律）
- 候选压缩（含 git 大仓）：cevt(1.66G)/antai(701M)/ltc(516M)/xinyi(355M)/zhsq(262M)/lims(112M)/dawei(106M)
- 已有 Gitee 私有仓的双保险项目（charger 类似的处理过的不涉及此处）可压缩后降级删除；无远端项目（zhsq/lims/dawei 等）压缩包即唯一副本，SHA256 清单必须落盘
- py7zr 金标准校验 + recycle.py 入回收站 + 用户检查后清空——flutter 事故三红线全程生效
- 产出：瘦身记录更新 + _archive 清单刷新

### 阶段 R3 · 归档地封存（0.5 次会话）
- 全目录 7z 终包（可选）+ 根 README（终态说明：这是什么、为什么封存、怎么恢复）
- 选项 A：目录保留在 D:\projects 原地（推荐，亿方云已核实不在同步范围）
- 选项 B：整体迁入 `D:\projects\_archive\` 深冻

### 素材实录（2026-09-07，R1 定版+R2 全执行当天）

- **数字**：projects-old 4045→2595MB（19 包 7z+SHA256 清单，2.6G 归档正中预估区间）；vue_front_project 3345→145MB；两线合计释放 ~7GB
- **事故钩子三个（真实发生）**：①回收站 FIFO 惊魂——vuefront 删的 3.1GB 原件被配额挤出站，「进了回收站=安全」是错觉，清站前对账才发现；②回收守卫 bug——脚本把「路径不存在」当「删除成功」，乌龙差点当战果；③SHFileOperation rc=120/32——Defender 瞬时句柄致目录回收失败，逐件+延时重试兜底
- **铁律候选**：回收站不是备份，校验过的归档+SHA256 清单才是 / 「删除成功」先证明「曾经存在」/ 归档单一根+总索引 / 数字要诚实（git pack 压不动，4G→2.4G 别吹 2G）
- **配方流程**：两层终态形态 → 三选一处置表 → 三批次（试点→中型→大型，每批金标准校验+回收站）→ 单根归档+总索引 → 7z 镜像/私有仓/工具提取四层兜底
