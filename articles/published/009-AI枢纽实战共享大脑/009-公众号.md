# 给 7 个 AI 造一个「共享大脑」：多智能体记忆治理实战（AI 枢纽实战·Ⅳ）

> 摘要（公众号摘要字段，≤120 字）：同一个项目，三个 AI 工具记的路径、版本、启动命令全不一样。记忆漂移不是意外，是默认状态。这篇讲怎么给 7 个 AI 造一个共享大脑，以及一套能把漂移揪出来的对账机制。

> 「AI 枢纽实战」系列·Ⅳ | POC 篇讲验证假设，MVP 篇讲到能用，自运维篇讲自己照顾自己。这一篇钻到最深的一层：7 个 AI 各有一套记忆，怎么让它们对同一件事说同样的话。

---

## 一、引子：三个 AI，三种说法

给枢纽接入第 4 个项目时，我让它做一次环境核查。结果三个 AI 工具给出的答案是这样的：

```
工具 A：项目用的是 MySQL 8，启动命令是 mvn spring-boot:run
工具 B：数据库是 PostgreSQL 16，启动要加 -Plegacy-mom-all
工具 C：数据库 PostgreSQL，端口 5432，前端跑在 3000
```

**同一个项目，三种说法。**

追查下去发现：项目两个月前就从 MySQL 迁到了 PostgreSQL、模块数从 10 个变成 16 个。**但每个 AI 工具的记忆里，都停在不同时刻。**

- 工具 A 记住的是三个月前的快照
- 工具 B 部分更新过，但启动命令还是旧的
- 工具 C 记得端口，但不知道后来加了大屏模块

这不是哪个 AI 的错。**是"各自为政的记忆机制"的必然结果**——每个工具都按自己的节奏记录，谁也不知道别人记了什么，更不会有人去核对。

> **核心洞察：在多智能体协作里，记忆漂移不是意外，是默认状态。**

---

## 二、为什么会漂移（先理解机制，再谈治理）

每个 AI 工具都有自己的"记忆"方案：有的存 `.workbuddy/memory/`、有的存 `AGENTS.md`、有的存 `.zcode/`、有的存 `.agnes/memories/`。它们是这么工作的：

```
AI 读完项目 → 自己总结 → 写进自己的记忆文件
    ↓
下次会话 → 读自己的记忆 → 基于它干活
```

问题在哪？**"自己总结 → 自己消费"是闭环的**——没有任何交叉验证。于是：

1. **时间差**：A 工具上周记的，B 工具这周才去读——中间项目变了
2. **视角差**：A 关心后端，B 关心前端——各自记住的切片不同
3. **无对账**：谁都没义务核对"别人的记忆"对不对

**结论：指望各家的记忆机制自我修正，是不可能的。必须有一个外部的"共享大脑"。**

---

## 三、共享大脑的设计：单一事实源

治理的第一步不是写机制，而是定规矩：**所有"事实"只允许有一个出处。**

于是有了 `knowledge/facts.md`——**枢纽的单一事实源**。规矩很简单：

```
✅ 客观事实（环境/路径/端口/版本/凭据位置）→ 写进 facts.md
❌ 不允许散落在各 agent 的私有记忆里（私有记忆可以"引用"，不能"定义"）
```

写入格式统一为一条条带来源的事实：

```markdown
- **cwjt（MOM 后端）**：`D:\projects\cwjt`，Java17 + Spring Boot 3；
  **实际数据库 = PostgreSQL**（多 schema 单库 cwjt-prod）；
  **实际模块 = 16 个**（mom-boot/common/eam/iot/mdm/mes/plan/...）
```

**为什么这一步就解决了 60% 的问题？** 因为"单一事实源"把一个**分布式一致性问题**（7 个 AI 各自记忆）降维成了**单一文件维护问题**——后者的难度低一个数量级。

但只定规矩还不够——**规矩会不会被遵守、事实会不会过期？** 这需要第二层机制。

---

## 四、记忆对账：把漂移揪出来的机制

漂移的可怕之处是"静默"——它不报错，只是慢慢让 AI 们说出矛盾的话。所以要有一个**定期对账机制**：

```
① 生成对账任务卡（每月自动）
② 派给一个 AI 审计员：扫描各项目的全部记忆载体
   （.workbuddy/memory、AGENTS.md、.zcode、.agnes、项目文档…）
③ 与 facts.md 逐条比对 → 产出漂移清单
④ 产出"机器可读的修正清单"（老值→新值，精确到字节）
⑤ 派给有写权限的 AI 执行修正 → 复核
```

**第一次运行就抓到真东西**：4 个项目、6 处核心漂移——

| 项目 | 漂移内容 |
|------|---------|
| cwjt | 记忆里还写着 MySQL（实际已迁 PostgreSQL） |
| cwjt | 模块数写着 10 个（实际 16 个） |
| hcmom | PG 版本过时（记得 15，实际 18.3） |
| hcmom | 演示环境 IP 还是旧的 |
| ... | ... |

**每条漂移都有精确的"老值→新值"和证据**——比如"记忆写 MySQL，证据：pom.xml 无 mysql 依赖、application.yml 是 PG 驱动"。

### 两个设计细节（很关键）

**① 审计员和修正员分离**

审计的 AI 只有读权限，修正的 AI 有写权限——**不能让同一个 AI 既发现问题又改问题**（它可能"顺手"改错或掩盖）。

**② 修正清单是机器可读的**

```yaml
- file: ".workbuddy/memory/MEMORY.md"
  old: "数据库：MySQL 8.0"
  new: "数据库：PostgreSQL（cwjt-prod 单库多 schema）"
  note: "迁移已完成，证据见 facts.md cwjt 条目"
```

`old` 要求**字节级精确**（配不上就不改，防误伤）——这套机制后来成了我们的标准动作。

## 五、分层记忆：让"经验"也能共享

事实解决了"客观信息"，还有一层更微妙的：**经验**。

A 工具踩过的坑，B 工具下次还会踩——除非经验能跨工具流动。于是有了分层记忆架构：

```
canonical/memory/
├── global/experiences/   ← 全局经验（任何 AI 都可贡献/消费）
├── projects/<项目>/      ← 项目级记忆
└── agents/<agent>/       ← 各 agent 自己的记忆（保留个性）
```

配套机制：

- **经验收割**：任务成功后自动从产出物里提取经验，写入 `global/experiences/`
- **记忆同步**：定期把各 agent 的私有记忆同步到分层结构中
- **行为规矩权威版**：全员的硬规矩放 `canonical/rules/behavior.md`（各 agent 规则文件引用它，避免多处维护）

**"个性"和"共识"分层**——每个 AI 保留自己的工作记忆，但"事实"和"经验"必须汇入公共层。这是共享大脑的完整形态。

## 六、治理效果：用数字说话

治理机制上线后的状态：

```
✅ 单一事实源：facts.md（21KB，全量环境/路径/凭据位置事实）
✅ 对账机制：月度自动审计（审计员/修正员分离）
✅ 分层记忆：全局经验 + 项目记忆 + agent 私有
✅ 首轮战果：4 项目 6 处漂移全部修正 + 独立复核通过
✅ 防复发：新事实强制写入 facts.md（规矩已进各 agent 的规则注入）
```

现在问任何一个接入的 AI"这个项目用什么数据库"，它读到的都是同一份事实。

## 七、可带走的配方（多智能体记忆治理）

**配方 1：单一事实源**
所有客观事实只允许一个出处（引用可以多，定义只能一处）。这一条把分布式一致性问题降维成单文件维护。

**配方 2：定期对账**
漂移是静默的，必须主动扫描比对。对账要产出"机器可读的修正清单"（老值→新值 + 证据）。

**配方 3：职责分离**
审计（只读）与修正（写）分离——发现问题的人不负责改问题。

**配方 4：事实与经验分层**
事实（共识）与经验（可共享）进公共层；各 AI 的工作记忆保留个性。不要追求"完全统一"。

---

## 三条铁律

1. **记忆漂移是默认状态，不是意外**——不治理就会漂
2. **没有单一事实源的协作，等于没有事实**
3. **对账清单要精确到字节**——模糊的修正清单会制造新漂移
