# 半天验证一个疯狂想法：让多个 AI 智能体自己协作（AI 枢纽实战·上）

> 摘要（公众号摘要字段，≤120 字）：装了 8 个 AI 编码工具，跨工具协作却全靠我人肉搬运。动手建系统前，我先花半天做了个 POC，只验证一条根本假设：文件协议能否驱动智能体自己协作。

> 「AI 枢纽实战」系列·上 | 这是一个真实项目的开篇：我没有直接动手建系统，而是先花半天做了个 POC，验证一个核心假设。结果它成了后面 19 天、4800 行代码、7 个 AI 执行方的起点。

---

## 一、起因：我成了 AI 的"人肉总线"

我的电脑上装了至少 8 个 AI 编码工具——OpenCode、Codex、ZCode、DeepSeek、Hermes、pi……

每一个都很能干。但问题出在**它们之间**：

- 在 A 工具里讨论清楚的方案，到 B 工具里要重新讲一遍
- 项目的事实散落在各处：这个工具记的路径是对的，那个工具记的还是三个月前的
- 谁擅长什么全凭印象，任务派给谁靠拍脑袋
- 最要命的是：**每次跨工具协作，我就是那个总线**——人肉复制上下文、人肉同步进度、人肉传递结论

于是有了一个想法：

> **能不能让这些智能体自己协作？让文件系统当总线，而不是我？**

想法很诱人。但在动手建系统之前，我先问了自己一个问题：

**这个想法的核心假设是什么？能不能用最小代价验证它？**

---

## 二、把想法拆成一个可验证的命题

任何一个"疯狂想法"都可以拆成一组假设。我的想法里，最核心、最不确定的是这一条：

> **假设：智能体能通过"读写约定好的 Markdown 文件"完成协作——即文件协议能替代人肉搬运。**

为什么先验证这一条？因为其他都是工程问题（可以慢慢做），只有这条是**根本性的**——如果智能体读不懂/不愿写文件协议，后面全都白搭。

**POC 的设计由此确定：**

```
验证单元（最小）：
  投一张任务卡（Markdown 文件）
    → 智能体自己读卡、干活、写报告
    → 回写状态、更新交接单
  = 四个文件落点全部自动完成，全程零人工
```

这四个落点我称为"四落点"：

| 落点 | 内容 | 为什么给智能体定这个 |
|------|------|---------------------|
| ① 产出报告 | `outputs/<agent>/<日期-主题>/report.md` | 有交付物，可追溯 |
| ② 任务卡回写 | status → done + 结果摘要 | 有状态，可调度 |
| ③ 交接单联动 | `handoff/H-latest.md` 追加记录 | 有上下文，下个智能体能接 |
| ④ 变更日志 | `PROGRESS.md` 追加一行 | 有历史，人能审计 |

**关键洞察**：这四个落点不仅是"要求智能体做什么"，更是**我的验收标准**——机器可校验（文件在不在、字段全不全），不依赖智能体"自报完成"。

（这一点后来被反复证明是对的——后面有智能体两次自报 DONE 但零产出，全靠四落点校验拦下。）

---

## 三、POC 的最小实现：只用三个东西

定好验证单元，接下来做最小实现。我给自己划了红线：**POC 不建系统，只验证假设**。

于是整个 POC 只有三块：

**1. 一个共享库（~200 行 Python）**

只做最核心的事：

```python
# 建任务卡（自动编号 T-YYYY-MMDD-NN）
create_card(agent, title, body)

# 解析任务卡（frontmatter + 正文）
parse_card(path)

# 找待执行的卡
find_cards(status="pending")

# 四落点校验（POC 的灵魂）
verify_card(card)  →  [(落点名, 是否通过), ...]
```

**2. 一个适配器（~50 行）**

把一张任务卡"喂"给智能体：调它的无头模式 + 一段标准指令。

```python
# 核心就一行：让智能体自己读卡干活
prompt = f"读取任务卡 {card['path']} 并严格执行。完成后写报告到 outputs/、回写 status=done、更新交接单和变更日志。"
subprocess.run([exe, "run", "--format", "json", "-"], input=prompt)
```

**注意这个设计**：适配器不告诉智能体"怎么做"，只告诉它"卡在哪、规矩是什么"——**智能体自己读卡、自己干活、自己落盘**。这正是要验证的东西：它能不能自己完成这一切。

**3. 一张自检任务卡**

让智能体给自己做一次接入自检。

**就这些。没有调度器、没有通知、没有数据库、没有守护进程。**

## 四、第一次运行：踩的第一个坑

信心满满地按下运行——报错：

```
FileNotFoundError: [WinError 2] 系统找不到指定的文件
```

查了半天原因，这个坑后来成了我们的"铁律"第一条：

> **Windows 下很多 CLI 是 `.CMD` 垫片脚本，Python 的 subprocess 不能直接执行它**（PATHEXT 不会被解析）。

修法：用 `shutil.which()` 拿到真实路径 + `.cmd` 后缀时经 `cmd.exe` 包装。

（这个坑极小，但它的"变体"日后埋伏了三次——`cmd /c` 包装会让超时失效、参数里的 `&` 会被截断、子进程会成为孤儿阻塞管道。最终的解法是彻底弃掉包装、直调真身，那是后话。**小坑早踩早好，是 POC 的价值之一。**）

---

## 五、第二次运行：假设成立

修好后重跑，三个落点依次亮起来：

```
[1] T-2026-0824-01  opencode-selfcheck.md
>>> 执行 T-2026-0824-01 ...
<<< T-2026-0824-01 完成 [PASS]
```

用校验器独立验证：

```
产出物规范 4.3  →  outputs/opencode/2026-0824-selfcheck/report.md  ✅（frontmatter 四字段齐全）
任务卡回写      →  status: done + 结果摘要已填                       ✅
交接单联动      →  H-latest.md "已发生"有记录                        ✅
```

**全流程零人工记忆参与**——适配器发现待执行卡 → 调起智能体 → 智能体自己读规范、干活、落盘、回写。

那一刻我确认：**假设成立**。文件协议确实能驱动智能体协作，"人肉总线"可以被替换掉。

---

## 六、POC 阶段的三个关键决策（为什么值得抄）

POC 只花了大半天，但里面有三个决定后来一直被沿用：

**决策 1：为什么用 Markdown 文件而不是 API/消息队列？**

因为协作的对象是**异构的**——不同厂商的智能体，接口千差万别。文件是唯一的"最低公分母"：
- 每个智能体都有文件工具（read/write/edit）
- 人可以直接看、直接改、直接 diff
- 没有黑盒：出问题就看文件
- 天然可审计（git 友好）

**决策 2：为什么要"四落点校验"而不是相信智能体自报"完成"？**

因为 LLM 会**礼貌地撒谎**——它可能说"已完成"而实际什么都没写。四落点是机器可校验的硬标准，把"完成"的定义权从智能体手里拿走。

**决策 3：为什么 POC 就要定"协议"（卡/交接单/报告的格式）？**

因为协作的本质是**约定**。POC 阶段就把三种文件的格式定死，后面的智能体接入就变成"照着格式写"，而不是"每次重新谈判"。

（后来我们接了 7 个执行方——每个接入成本约 30 分钟，靠的就是这个协议不变。）

## 七、POC 结论：进入 MVP 的信号

POC 结束时的状态：

```
✅ 核心假设验证：文件协议驱动协作 —— 成立
✅ 最小闭环跑通：投卡 → 执行 → 四落点全 PASS
✅ 坑已归档：Windows .CMD 垫片问题（并为日后三次变体埋下预警）
❌ 还不能日常用：没有调度器（每张卡手动跑）、只有一个智能体、没有通知（跑完不知道）
```

**这就是 POC 的正确终点**——不是"系统建好了"，而是"**最大的不确定性消除了**"。此刻再投入做 MVP，风险已经从"想法是否成立"降级为"工程是否扎实"。

## 八、可带走的方法论

如果你也想验证一个复杂想法，这套 POC 思路可以直接抄：

**1. 找到"根本性假设"**
你的想法里，哪一个假设不成立就全盘皆输？（我的：文件协议能驱动协作）——POC 只验证它，其他都是工程问题。

**2. 把假设翻译成"可观测的验证单元"**
不要验证"想法"，要验证"现象"。（我的：四落点是否自动全 PASS）

**3. 划红线：POC 不建系统**
调度器、通知、守护进程全部延后。POC 的代码量应该小到"验证完就可以扔掉"。（我的：~250 行）

**4. 验收必须机器可校验**
"智能体说完成了"不算数，"文件在、字段全"才算数。

**5. POC 的产出不是代码，是"确定性的迁移"**
从一个高风险假设，迁移到一个低风险工程问题。
