# GUI 的 AI 工具就活该被自动化排除吗？三种接入形态实测（AI 工具实测·下）

> 摘要（公众号摘要字段，≤120 字）：上一篇说"可无头"是一票否决项。但我手里还有几个没有无头模式的 GUI 工具——它们真的用不上吗？实测下来，我总结出了三种协作形态，最"原始"的那种反而最通用。

> 「AI 工具实测」系列·下 | 上篇的结论有点狠：没有无头模式 = 进不了自动化流水线。这篇是那个结论的"补丁"——GUI 工具不是不能用，是用法不同。

---

## 一、引子：我手上的"二等公民"

上一篇总结的选型标准里，"可无头"是一票否决项。但我本机还有一批没法无头调用的 AI 工具：

- 一个桌面版 AI 工作台（有完整的智能体能力，但只有图形界面）
- 一个 AI 编程应用（引擎很强，但没有命令行入口）
- 一个纯网页的 AI 办公产品（连本地文件都碰不到）

按上篇的标准，它们全部"不合格"。

但我不甘心——**它们里面有真能干活的**。于是我做了一轮实测：**这些 GUI 工具，怎么按同一套文件协议协作？**

结果发现：**它们不是"能不能接入"的问题，而是"用哪种形态接入"的问题。**

---

## 二、先说结论：三种形态

实测下来，GUI 类工具可以分成三种协作形态：

| 形态 | 特征 | 触发方式 | 完成度 |
|------|------|---------|--------|
| **① 本地文件型** | 能读写本地文件 + 有智能体能力 | 人工贴一次指令 | **四落点自主完成** |
| **② GUI 专属型** | 能读写本地文件，但只能在自己的界面里跑 | 人工在界面里喂任务 | **四落点自主完成** |
| **③ 人肉协议型** | 纯 SaaS，无法访问本地文件 | 人工搬运内容 | **文本产出合格（落盘由系统代劳）** |

**关键洞察**：三种形态用的是**同一套任务协议**——变的只是"触发方式"和"谁来落盘"。**协议不变，形态递减。**

下面逐个讲实测过程。

---

## 三、形态一：本地文件型（最理想）

**样本**：一个桌面版 AI 工作台（安装在本地，自带智能体运行时 + 一堆技能）。

**能力**：它是完整的智能体形态——有文件读写工具、有技能体系、能理解复杂指令。

**实测过程**：

我给它建了一张标准任务卡（和给无头执行方的一模一样），然后**人工把指令粘贴到它的对话框**：

```
读取 D:\projects\agent-hub\tasks\T-xxx.md 并严格执行其中全部步骤。
```

**结果超出预期**：

```
✅ 落点① 产出报告：自己写进了指定目录
✅ 落点② 任务卡回写：自己改 status=done 并填了摘要
✅ 落点③ 交接单联动：自己追加了记录
✅ 落点④ 变更日志：自己写了变更日志
```

**四落点 4/4 自主完成**——除了"启动"是人工粘贴的，其余全自动。

**它的实际定位**：**"人工触发 + 全自动执行"**。人只需要做一件事（贴指令），剩下的和 L2 无头执行方一样。

---

## 四、形态二：GUI 专属型（能用但没有门）

**样本**：一个 AI 编程应用（引擎很强，智能体多角色协作）。

**探查过程**（想找它的无头入口）：

```
① 试它的命令行主程序 → 直接拉起图形界面（不是 CLI）
② 试它自带的工具型 CLI → 只是登录/上传等辅助功能，不是智能体入口
③ 翻它的运行时目录 → 有完整智能体会话数据，但没有可调用的入口
```

**结论**：它是**"GUI 专属"**——引擎完整，但没有任何程序化入口，只能在自己的界面里跑。

**但它仍能按协议协作**（和形态一同样的方式）：人工在它的界面里喂任务卡 → 它自己完成四落点。

**实测结果**：四落点 4/4 自主完成。

**它的定位**：和无头执行方只差**"一个可编程入口"**。如果有朝一日它出了 CLI，五分钟就能升级成完全自动。

---

## 五、形态三：人肉协议型（最原始，但最通用）

**样本**：一个纯网页的 AI 办公产品（SaaS，本机零安装）。

**探查**：连本地文件都访问不了——是个纯浏览器沙箱。

**这怎么办？** 换个思路：**它的产出能力是有的（写文案/报告），只是"文件流转"需要人。**

于是有了"人肉文件协议"：

```
人：把任务要求粘贴给它
  → 它：产出文本（报告/分析）
  → 人：把文本复制回来
  → 系统：代为落盘 + 完成四落点
```

**实测结果**：

```
✅ 文本产出：合格（内容质量不差）
✅ 协议闭环：报告落盘 / 状态回写 / 交接单 / 变更日志——由系统代劳
⚠️ 区别：多了"人工搬运"环节，且搬运的是内容不是文件
```

**它的定位**：**文本产出型**——适合"要内容"的任务（周报/文档/分析），不适合"要落盘/要交互"的任务。

**看起来最原始，但它最通用**：门槛最低（只要有个能对话的 AI），任何 SaaS 都能套这个形态。**"最原始"等于"最没有前提条件"。**

---

## 六、三形态的统一与差异

把三种形态放在一起看：

| 环节 | 形态一（本地） | 形态二（GUI专属） | 形态三（人肉） |
|------|:---:|:---:|:---:|
| 任务协议 | 同一套 | 同一套 | 同一套 |
| 触发 | 人贴指令 | 人喂界面 | 人贴内容 |
| 读文件 | ✅ 自主 | ✅ 自主 | ❌ 做不到 |
| 干活 | ✅ 自主 | ✅ 自主 | ✅ 自主 |
| 落盘 | ✅ 自主 | ✅ 自主 | ⚠️ 系统代劳 |
| 回写 | ✅ 自主 | ✅ 自主 | ⚠️ 系统代劳 |

**最重要的发现**：**协议（任务卡格式/四落点契约）从头到尾没有变过。**

变的只是"哪一环由人补位"：

```
形态一：人补"启动"这一环
形态二：人补"启动"这一环（且只能在GUI里）
形态三：人补"启动 + 搬运 + 落盘"
```

**这就是"分级接入"思想的精髓**——不是"完美自动化或不用"，而是**"缺哪环补哪环"**。

---

## 七、可带走的配方（GUI 工具接入清单）

**配方 1：先探"有没有门"**
按顺序试：① 主程序的命令行参数 ② 自带的工具型 CLI ③ 运行时目录里有没有可调用入口。都没有 → 归 GUI 类。

**配方 2：能读写本地文件的，按"人工触发 + 全自动执行"接**
建标准任务卡，人工把"读卡指令"粘进去——之后它自己完成四落点。

**配方 3：碰不到文件的，走"人肉协议"**
人搬内容、系统代落盘。协议闭环不变，只是多一道人工环节。

**配方 4：协议不变，触发分级**
同一套任务格式覆盖所有形态——降低"接入"的心智成本（学一次，到处用）。

**配方 5：给 GUI 工具留"升级位"**
所有 GUI 工具都登记在案（含"如果它出 CLI，怎么升级"的备注）——工具生态会变，留个位子。

---

## 三条铁律

1. **"不能自动化" ≠ "不能协作"**——缺的环节人可以补
2. **协议统一，触发分级**——一套格式覆盖全形态
3. **最原始的形态最通用**——人肉协议的零前提，覆盖任何 SaaS
