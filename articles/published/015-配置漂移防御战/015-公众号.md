# 配置漂移防御战：为什么"昨天能跑"的东西今天挂了（自动化硬核·Ⅲ）

## 一、引子：一周内的五次"灵异事件"

自动化系统最怕的不是"一直坏"，是"昨天还能跑，今天莫名其妙挂了"。某一周，我经历了五次：

```
周一：某个 AI 工具的新会话全部报错
周二：另一个工具的启动直接拒绝（说找不到 provider）
周三：第三个工具配置解析失败
周四：某个工具的行为突然变了个样（沙箱模式被改）
周五：某个执行方的任务全部失败（认证错误）
```

五次故障，表象各异。**但根子是同一个**：配置漂移。

> **核心认知：在自动化的世界里，"外部依赖"（工具/服务/凭据）的配置是活的——它会变，而且通常是静默地变。**

这篇把五次事故拆开讲，然后给一套防御配方。

---

## 二、五种死法（真实案例）

### 死法一：上游把模型下线了

**现象**：一个 AI 工具的新会话全部报错（"server error"），但在别的地方用同一个工具正常。

**追查**：工具配置里**没有显式指定模型**——它"跟随默认"。而"默认"指向的那个免费模型，被上游**悄悄下线了**。

**根因**：不写死配置 = 把控制权交给上游。上游一变，你就跟着挂。

**修复**：显式固定模型（写进配置文件），不依赖"默认值"。

### 死法二：配置指向了一个"不存在的选项"

**现象**：另一个工具启动就拒绝，报"没有注册的 provider"。

**追查**：它的配置里，"默认模型"指向一个叫 `minimax-m25` 的 provider——但配置里**注册的 provider 列表**根本没有这一项。

**怎么会这样？** 大概是某次配置调整时改了一半：新选项没注册、默认值先改了。**平时没人发现**（因为它只在"启动"时才校验），直到某次重启。

**修复**：把默认值改成已注册的 provider。**同时加"启动前校验"**（见下文配方）。

### 死法三：schema 格式漂移（一个字段，两种写法）

**现象**：工具配置解析失败，报格式错误。

**追查**：配置文件里有一个字段，**旧版接受"对象"写法，新版接受"字符串"写法**——工具升级后，旧配置格式失效了。（升级工具时，配置格式变了，但配置没跟着变。）

**修复**：按新版文档改配置格式。

### 死法四：配置被"第三方"静默改写

**现象**：某个工具突然行为异常——它之前工作的沙箱模式变了。

**追查**：那个工具的配置**被另一个软件改写了**（一个多工具管理类的软件，会在切换时"顺手重置"某些配置项）。**它甚至提示都没提示。**

**根因**：你的配置文件可能有多个"作者"——你、工具自己、以及管理工具。**任何一方都可能在你不察觉时改它。**

**修复**：改回正确值 + （重要）**在调用代码里显式传参覆盖**，不完全依赖配置文件（代码里的参数优先级高于配置，管理工具改配置也影响不了）。

### 死法五：凭据悄悄过期

**现象**：某个执行方的任务全部失败，报认证错误。

**第一反应**："工具坏了？"——查下去发现：**它的 API key 失效了。**（可能额度用完、可能轮换过、可能达到有效期。）

**根因**：凭据有生命周期，而系统**没有"到期意识"**。

**修复**：换新的凭据；**更重要的**——把凭据纳入巡检（提前预警，而不是等它断了才发现）。

**注**：这条最容易被误判——**"执行方失败"看起来像代码问题，实际是环境问题。**

## 三、漂移的三类来源（归类）

五个案例可以归成三类来源：

| 来源 | 案例 | 特征 |
|------|------|------|
| **上游变化** | 模型下线（死法一） | 你什么都没做，外部服务变了 |
| **多写者改写** | 管理工具重置（死法四） | 配置文件有多个"作者" |
| **自身状态老化** | 凭据过期（死法五）、配置与版本脱节（死法二/三） | 时间在流逝，环境在变化 |

**三类都无法"杜绝"**——上游你管不了、第三方软件你拦不住、时间不会停。**所以防御的方向不是"让配置不变"，而是"让变化被快速发现"。**

## 四、防御配方：调用前探测 + 快速失败 + 人话诊断

核心思想一句话：**不要相信"上次能跑"，每次关键调用前花一秒钟探测。**

### 配方 1：调用前廉价探测

在"真正干活"之前，先跑一个**便宜、快、只读**的检查命令：

```python
def probe_tool_ready():
    """调用前探测：配置是否完好、凭据是否有效（1 秒内完成）"""
    r = subprocess.run([tool, "config", "show"], capture_output=True, timeout=10)
    if r.returncode != 0:
        return False, "配置读取失败"

    r = subprocess.run([tool, "auth", "status"], capture_output=True, timeout=10)
    data = json.loads(r.stdout)
    if not data.get("authenticated"):
        return False, "凭据无效或已过期"
    return True, "ready"
```

**为什么值得**：探测失败**一秒就知道**；不探测的话，你要等它跑起来、错了、再排查——可能几分钟后才知道"根本跑不了"。

**探测要选"廉价"的**：`--version` / `config show` / `auth status` 这类——不干活、不花钱、不耗时。

### 配方 2：快速失败 + 独立退出码

探测失败时**立刻返回**，并给一个**专属退出码**（区别于"工具自己报的错"）：

```python
PROBE_FAILED = 87   # 自定义：探测失败（不是任务的失败）

def run_task(card):
    ok, detail = probe_tool_ready()
    if not ok:
        return CompletedProcess(args=[], returncode=PROBE_FAILED, stdout="", stderr=detail)
    ...  # 真正干活
```

**好处**：上层（调度器）看到退出码 87 就知道"这是'环境没准备好'，不是'任务失败'"——**处理策略不同**（前者该通知人去修环境，后者该重试/改派）。

### 配方 3：人话诊断（给"下一步动作"）

探测失败时，错误信息必须是**人能直接照做的**：

```python
# 坏诊断：只报现象
"EPERM: operation not permitted"

# 好诊断：说清原因 + 修复动作
"工具无法启动：配置文件不可写（EPERM 预判）。
 该工具每次启动都会重写配置，必须运行在无沙箱环境。
 请在普通终端（非受限沙箱）中调度。"
```

**原则**：**诊断信息里必须有"怎么办"**——不要把"谜语"丢给半夜排障的人（包括未来的自己）。

### 配方 4：在代码里固定关键参数（防第三方改写）

对于"被第三方静默改写"那类问题——**关键参数在调用命令里显式传**：

```python
# 配置可能被改 → 命令行参数直接覆盖（优先级更高）
subprocess.run([tool, "exec", "-c", 'sandbox="unelevated"', ...])
```

**命令行参数 > 配置文件**——这是大多数工具的参数优先级规则，善用它。

### 配方 5：凭据纳入巡检（提前预警）

给凭据加"到期倒计时"监控：

```python
days_left = (expiry_date - now).days
if days_left <= 7:
    alert(f"凭据还有 {days_left} 天过期，请续期")   # 提前 7 天预警
```

**从"断了才发现"变成"到期前预警"**——这是我在经历"凭据静默断线 10 天"之后加的第一道防线。

## 五、一个反直觉的结论

认真对待配置漂移之后，我意识到一件事：

> **"稳定"不是环境的属性，是你加了多少"探测"的属性。**

外部世界永远在变（上游下线、软件改写、凭据老化）。一个"稳定运行"的自动化系统，不是因为它依赖的东西稳定——**而是因为它对这些变化"敏感"**（能快速发现）+"健壮"（发现后快速失败而非崩溃）。

**稳定 = 敏感 + 健壮，不是"依赖不变"。**

## 六、可带走的配方（汇总）

| 配方 | 一句话 |
|------|-------|
| 调用前探测 | 关键调用前跑廉价检查（config/auth/version） |
| 快速失败 | 探测失败立刻返回，专属退出码（87） |
| 人话诊断 | 错误信息必须包含"修复动作" |
| 参数覆盖 | 关键参数命令行显式传（防第三方改写配置） |
| 凭据巡检 | 到期倒计时，提前 7 天预警 |
| 显式固定 | 不依赖"默认值"（上游一变你就挂） |

---

## 三条铁律

1. **不要相信"昨天能跑今天就能跑"**
2. **配置有多个"作者"——你、工具、以及管理工具**
3. **稳定不是环境给的，是"探测"给的**
