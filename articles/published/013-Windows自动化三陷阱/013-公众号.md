## 陷阱一：`.CMD` 垫片 —— 找不到的文件

### 现象

Python 里调用一个命令行工具，直接报错：

```
FileNotFoundError: [WinError 2] 系统找不到指定的文件
```

但诡异的是——**在终端里手敲同样的命令，完全正常**。

### 根因

那个命令（比如 `opencode`）在 npm 全局安装后，生成的不是 `.exe`，而是 **`.cmd` 批处理垫片**：

```bat
@ECHO off
GOTO start
:start
node "%~dp0\node_modules\opencode-ai\bin\opencode.js" %*
```

它是一个**批处理脚本**，不是可执行程序。

而 Python 的 `subprocess` 在 Windows 上**不解析 `PATHEXT`**（也就是不认 `.cmd`/`.bat` 这些"可执行扩展名"）——你给它一个没有扩展名的 `opencode`，它找不到对应的文件；你给它 `opencode.cmd`，它也不会用批处理解释器执行。

**"终端里能跑"是因为终端（cmd/PowerShell）懂垫片，"Python 直接调用"不懂。**

### 修复

两条路，推荐第一条：

```python
import shutil
from pathlib import Path

def build_command(cmd_name, args):
    # 路线一（推荐）：解析出真实入口，直接调用
    # 对于 node 工具：用 node + 真实 js 文件
    js = Path(r"...\node_modules\xxx\bin\cli.js")
    node = shutil.which("node")
    if node and js.exists():
        return [node, str(js), *args]

    # 路线二（兜底）：找到 .cmd 就走 cmd /c 显式执行
    exe = shutil.which(cmd_name)   # 这一步能找到 .cmd 全路径
    if exe and Path(exe).suffix.lower() in {".cmd", ".bat"}:
        return ["cmd.exe", "/c", exe, *args]
    return [exe, *args]
```

**为什么推荐路线一？** 因为路线二（`cmd /c`）会引出**下一个更阴险的坑**。

## 陷阱二：`cmd /c` 让超时失效 —— "挂起"的命令

### 现象

修好陷阱一之后，用 `cmd /c` 包装运行一个 AI 工具的命令。然后：

- 命令跑了 30 分钟没动静，判定"挂起"
- 手动杀掉，重试
- 后来发现：**那 30 分钟里，任务其实早就完成了**——产出文件都写好了

### 根因

`subprocess.run(..., timeout=60)` 的超时保护，在 `cmd /c` 包装下**只作用于 `cmd.exe` 本身**：

```
Python subprocess
    └── cmd.exe（超时杀的是它）
          └── 真实的 CLI 进程（它变成"孤儿"，继续跑）
```

Python 在超时后杀掉了 `cmd.exe`——但它**管不到 `cmd.exe` 的子进程**。真实 CLI 变成孤儿继续执行，而 Python 以为"命令被终止了"。

**结果：你以为超时生效了，其实只是"表层被杀"，里层还在跑**（甚至还在正常完成工作）。

### 修复

**能不用 `cmd /c` 就不用。** 优先走"直调真身"：

```python
# 不要这样（超时管不住真实进程）：
subprocess.run(["cmd.exe", "/c", "xxx.cmd", "arg"], timeout=60)

# 要这样（直调真实入口，超时真正生效）：
subprocess.run([node, cli_js, "arg"], timeout=60)
```

对于确实是 `.exe` 的工具，直接用绝对路径调用：

```python
exe = r"C:\Users\xxx\AppData\Roaming\npm\node_modules\opencode-ai\bin\opencode.exe"
subprocess.run([exe, "run", ...], timeout=60)
```

**验证方法**：超时后检查是否有孤儿进程残留（`tasklist` / `Get-Process`）——如果没有残留，说明超时真的生效了。

## 陷阱三：管道阻塞 —— 任务完成了，进程却等不到"结束"

### 现象

某个任务明明完成了（产出文件都在），但守护进程**卡了 16 分钟**才继续——差一点被判定为"死锁"。

### 根因预告

还是孤儿进程，但这次的手法更隐蔽：**孤儿子进程继承了你用来捕获输出的"管道"**，导致父进程一直等不到"管道关闭"。

这个坑的完整追查过程足够写一篇侦探故事（下一篇就是），这里先给结论：

### 修复方向

```python
# 危险写法：capture_output=True 用管道捕获输出
# 如果子进程留下了继承管道的孤儿 → 父进程等 EOF 永远等不到
subprocess.run(cmd, capture_output=True, timeout=3600)

# 安全写法：输出重定向到临时文件，wait 只等"目标进程本身"
import tempfile
with tempfile.TemporaryFile(mode="w+", encoding="utf-8") as out:
    r = subprocess.run(cmd, stdout=out, stderr=out, timeout=3600)
    out.seek(0)
    output = out.read()
```

**原理**：用管道时，父进程要等**所有持有写端的进程**都关闭管道才读到 EOF；用文件时，`wait` 只等**目标进程**退出——孤儿进程持有文件句柄完全不影响。

## 三个陷阱的共性（最重要的部分）

回头看，三个坑是同一件事的三种表现：

| 陷阱 | 假设 | 现实 |
|------|------|------|
| .CMD 垫片 | "命令 = 可执行程序" | 命令 = 包装脚本（子进程树） |
| 超时失效 | "杀父进程 = 杀整个命令" | 只杀表层，子进程成孤儿 |
| 管道阻塞 | "子进程退出 = 管道关闭" | 孤儿子进程仍持有管道 |

**核心认知：在 Windows 上，"一个命令"往往是一棵进程树，不是一个进程。** 你对子进程的所有假设（能找到、能杀干净、会释放资源）——都在包装层面前失效。

---

## 可带走的配方

**配方 1：直调真身**
调用 CLI 前先解析真实入口（node + js / exe 绝对路径）。`.cmd`/`.bat` 只用来"发现"，不用来"执行"。

**配方 2：审计你的超时**
所有 `subprocess` 超时**必须验证过"超时后无孤儿残留"**——否则超时是假的。

**配方 3：输出用文件，不用管道**
调用可能产生子进程的 CLI 时，`stdout/stderr` 重定向到临时文件，而不是 `PIPE`。

**配方 4：子进程直跑冒烟测试**
写测试实际启动进程、断言有输出——不要只 `import` 后调函数（测不出入口/包装层问题）。

---

## 三条铁律

1. **Windows 的"命令"常常是包装脚本，不是程序**
2. **`cmd /c` 会让超时和信号全部失效**——能直调就直调
3. **管子（管道）是共享资源，孤儿会攥着不放**
