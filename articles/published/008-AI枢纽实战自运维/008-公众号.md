# 当一个自动化系统开始自己照顾自己：从「能用」到「自运维」的 15 项进化（AI 枢纽实战·Ⅲ）

> 摘要（公众号摘要字段，≤120 字）：自动化系统的成年礼不是功能更多，而是能自己发现问题。一次凭据静默断线 10 天的教训、三次实测揪出的深层 bug、15 项纵深进化——这是一个系统学会照顾自己的全过程。

> 「AI 枢纽实战」系列·Ⅲ | 前两篇讲了 POC（半天验证假设）和 MVP（2 天到能用）。这一篇讲最长的第三阶段：当系统每天都在跑，它开始暴露一堆"没人盯着就会烂掉"的问题。

---

## 一、引子：MVP 之后，账单来了

MVP 结束时，系统每天都在跑。但用了一阵子，我发现它有一笔"隐形成本"——**它需要人照顾**：

- 凭据会过期（钉钉、飞书的 token 都有有效期）
- 知识库会膨胀（三个月前的日志还堆在文件顶上）
- 产出会失控（几十个目录里躺着几百个文件）
- 出了问题，得人来发现、人来修

**一个需要人盯着的自动化系统，本质上还是半自动。**

这个阶段的主题词是：**自运维**——让系统自己发现问题、自己保持健康、自己管理知识。下面讲的 15 项进化，全都围绕这一个目标。

---

## 二、转折点：一次静默断线 10 天

故事从一个"灵异事件"开始。

某天我给系统加通知通道，测试时发现飞书通、钉钉不通。查下去才发现：

> **钉钉的认证凭据早就过期了——而这条通知通道，已经静默断了 10 天。**

这 10 天里，系统每天都在正常干活、正常"完成任务"。**但它完成任务的所有通知，一条都没发出去。**没有报错、没有告警、什么都没有——因为它根本没在"检查"自己。

这件事教会我一个道理：

> **没有巡检的自动化系统是"盲"的。它只能发现"任务失败"，发现不了"我自己坏了"。**

于是第一项进化落地：**健康巡检**。

每天一次，检查五件事：

| 巡检项 | 检查内容 |
|--------|---------|
| 凭据健康 | 钉钉/飞书 token 有效性 + **到期倒计时**（不是等它断了，而是提前 7 天预警） |
| 通道配置 | 通知配置是否完好 |
| 执行方入口 | 7 个 AI 执行方的 CLI 是否都还在（被卸载/升级搞丢是常事） |
| 密钥泄漏 | 全库扫描明文凭据（4 类模式） |
| 自身状态 | 巡检结果落盘，供状态视图读取 |

**关键设计：巡检异常会主动推送告警**——比如凭据还有 7 天过期，你手机上就会收到提醒。从此再没有"静默断线"。

（巡检上线第一天就抓到一个真实问题：飞书的某个 token 状态异常。后来发现是正常的"自动刷新中间态"——顺手修正了误报逻辑。**巡检自己也被巡检了一遍。**）

## 三、自运维三件套

巡检解决了"发现问题"，还需要"看得清"和"算得清"。

**① 状态视图：一条命令看全局**

```
$ hub --status

【健康巡检】OK（检查于今天 16:02）
  [OK] 钉钉凭证：token 有效，refresh 剩 29 天
  [OK] 飞书凭证：bot+user 双身份 ready
  [OK] L2 执行方入口：7 个入口齐备
  [OK] 明文密钥扫描：61 文件，无泄漏

【任务统计】done: 12 / pending: 0
【收件箱】0 条待转
【凭据倒计时】钉钉 refresh：剩 29 天
```

以前要翻变更日志才能知道系统状态，现在一屏看完。

**② 归档体系：一场"清爽术"**

有次我盘点数据目录，发现一个惊人的数字：**65427 个文件**。

追查下去——某个 AI 执行方在跑任务时，把它自己的工作缓存（378MB 的依赖目录）写进了产出目录。而这样的"数字垃圾"还有一堆：

- 顶层散落的调试脚本
- 越来越长的变更日志（99KB）
- 历史交接单备份

清理的原则很关键：**清理 ≠ 删除，清理 = 归档 + 索引**。

于是建立了归档体系：

```
_archive/
├── INDEX.md          ← 总索引（什么/何时/为什么/怎么调用）
├── debug-scripts/    ← 调试脚本（含 README：每个文件来历+替代品）
├── dsh-home/         ← 缓存删除前的说明（怎么重建）
└── progress-2026-08.md  ← 历史日志（可检索）
```

**成果：产出目录 65427 → 163 个文件（-99.7%），知识零丢失。**

三条归档纪律从此立下：

1. 归档必登记索引（四要素）
2. 知识 > 缓存（删缓存前必须写明重建方法）
3. 活文档切割先备份

**③ 记忆防腐：知识库也要"体检"**

和文件膨胀同理，系统的"事实库"也会越写越乱：三个月的条目混在一起，过期的没清、旧的没归档。

进化：月度记忆审计（自动生成审计卡 → AI 执行审计 → 产出修正清单）+ facts 归档工具（分析候选 → 审查 → 精确归档）。

## 四、三次实测，三个深层 bug（这一节最值钱）

系统"自运维"能力建好后，我以为可以高枕无忧了。然后**三次真实使用**，每次都揪出一个藏得很深的 bug。

**实测一：任务完成后，守护进程卡了 16 分钟**

现象：一个任务明明完成了，但完成通知延迟了 8 分钟才发。

追查（看进程树 + 锁文件）：

```
发现 chain：
任务完成 → 但守护进程卡在等子进程
  → 子进程为什么没退出？它在等一个"管道"关闭
    → 管道为什么没关？因为 AI 执行方退出时，它的一个子进程（MCP 服务）没被回收
      → 孤儿进程持有管道 → 父进程等 EOF 永远等不到
```

这是经典的**孤儿进程管道阻塞**——四层防御修复：

1. 自研的常驻子进程加"父进程看门狗"（父死即自退）
2. 调度层改用临时文件捕获输出（不再等管道 EOF）
3. 所有子进程调用加超时兜底
4. 任务锁加"持有进程存活检测"（死进程的锁自动清理）

**实测二：总有个 cmd 窗口时不时弹出来**

用户反馈："为什么总有个 cmd 窗口时不时跳出来？"

根因：守护进程是以"无控制台"方式运行的（pythonw）——**它每次调用外部程序，Windows 都会给子进程分配一个新的控制台窗口** = 闪窗。而刚加的某项功能让调用频率变成了每 30 秒一次——从偶发变成"一直有"。

修复：所有子进程调用加"无窗口"标志（8 处）+ 开机启动从批处理改成 VBS 脚本（wscript 宿主无窗口）。

**实测三：AI 突然全线失败**

现象：某个执行方的任务全部失败。

第一反应"执行方坏了"——但查下去发现：

> **它的 API key 失效了。**

这是**环境问题伪装成代码问题**的典型案例。教训：

> 部署时永远先分层定位（代码 / 配置 / 环境 / 外部服务），再动手改。环境问题改代码，永远改不好。

**这三次实测的元教训**：

> **自动化测试保底，实测发现真相。** 108 个测试全绿，但它们测的是"逻辑正确"——**测不出进程行为、观感问题、环境漂移**。测试覆盖"逻辑正确"不等于"系统健康"，实测 + 巡检 + 用户观察，三层缺一不可。

## 五、工作流化：从"单任务"到"能编排"

系统早期一次只能调度一个任务，多步骤的活儿要人工串联。进化方向：**工作流**。

三个新能力：

**① 任务依赖**——任务卡可以声明"依赖某张卡"：

```yaml
depends_on:
  - T-2026-0910-02    # 等这张卡完成
```

依赖没满足的卡自动跳过；依赖完成后（守护进程下一轮）**自动接续执行**。实测：一条 A→B 的任务链，全自动跑完，零人工。

**② 失败处理链**：

```
失败 → 自动重试（可配次数）
     → 重试耗尽 → 自动改派（备选执行方链）
                → 无候选 → 标记"受阻"，通知人工
```

**③ 三重幂等**（并发问题的终极答案）：

```
① 依赖过滤：不该跑的不跑
② done 跳过：跑完的不重跑
③ 派发锁：正在跑的不并发
```

第③条是被现实教育的：有天守护进程和我手动命令**同时拉起同一张卡**，两个 AI 会话对着同一张卡抢着干活（其中还"礼貌地"向对方致意）。当天补上卡级锁。

## 六、把能力向外延伸

自运维之后，系统开始"长出手脚"——不只是内部健康，还能对外服务：

**📱 手机投任务（IM 入站桥）**

目标：人在外面，发条钉钉消息就能让 AI 干活。

过程有个波折：本来的方案是"监听钉钉消息事件"——但实测发现 **Windows 平台不支持那个长连接机制**（底层是 Unix 的实现）。改道：**轮询拉取模式**（每 30 秒增量拉一次消息）。

现在的体验：

```
你在钉钉群发：hub: 读一下项目状态并发我一份摘要
    ↓（30 秒内）
手机收到："✅ Hub 已收到任务"
    ↓（AI 执行完成）
手机再收到：任务完成通知（含结论摘要）
```

**🔌 MCP Server（让系统可被调用）**

把整个枢纽包装成 MCP 服务——任何支持 MCP 的 AI 客户端，都能直接调用"投任务/查状态/取报告"。实测用另一个 AI 客户端调用成功：它自己查到了系统状态并汇报。

**📊 周报 + 检索**

每周自动生成 Hub 周报（任务统计/变更摘要/健康/凭据倒计时）推送到手机；一条命令跨全部资料检索（任务卡/报告/知识库）。

## 七、知识资产化：写文档也是写系统

这个阶段做了三件"给系统留遗产"的事：

**① 技术文档（从零重建手册）**

737 行、13 章——设计哲学/架构/协议/逐模块实现/**8 步从零构建流程**/16 个已知坑。目标：任何人（或 AI）拿到它就能从零重建。素材来自 19 天的全部构建记录。

**② 经验教训集**

把 16 个真实问题提炼成三层知识体系：

```
原始记录（何时/何因/何解）
    → 铁律速查（现象→根因→做法）
        → 模式与认知提炼（为什么错/怎么想对）
```

**③ Git 规范化**

终于给项目上了版本管理（私有仓库）。规范包括：提交格式、**pre-commit 密钥扫描门禁**（防明文凭据入库）、文件入库规则（源入库/产物排除）。

顺带踩了个好坑：`.gitignore` 的规则行**不支持行尾注释**——我写了 `canonical/memory/  # 注释`，结果 git 把 `#` 后全部当模式的一部分，**规则静默失效**，24MB 垃圾险些入库。

教训入册：**配置生效 ≠ 配置写入了**——写完要验证行为（`git check-ignore -v` 确认命中），和"脚本打印成功≠改对了"同源。

## 八、结语：自动化的"成年"标志

回头看这 15 项进化，它们可以归成一句话：

> **一个自动化系统成年的标志，不是功能更多，而是能自己发现自己问题。**

对照检查：

| 能力 | 儿童期 | 成年期 |
|------|--------|--------|
| 发现故障 | 人发现 | 巡检自己发现并预警 |
| 保持清洁 | 人清理 | 归档体系自动维护 |
| 应对失败 | 人补救 | 重试/改派/阻塞自动处理 |
| 知识沉淀 | 人整理 | 文档自我完备（从零可重建） |
| 面对未知 | 人盯着 | 实测驱动自我修正 |

## 可带走的方法论（自运维篇）

**1. 没有巡检的自动化系统是"盲"的**
能发现"任务失败"不算本事，能发现"我自己坏了"才算。

**2. 清理 = 归档 + 索引，不是删除**
删除是粗暴的，归档是优雅的。关键在索引——"随时可调用"。

**3. 自动化测试保底，实测发现真相**
测试测"逻辑正确"，测不出进程行为/观感/环境。三层缺一不可。

**4. 环境问题会伪装成代码问题**
先分层定位（代码/配置/环境/外部服务），再动手。

**5. 三重幂等：不该跑的不跑、跑完的不重跑、正在跑的不并发**
第③条一定是被现实教育出来的。
