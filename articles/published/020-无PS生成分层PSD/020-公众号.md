## 引子：一个"没有软件怎么出格式文件"的问题

产品经理拿着折页设计稿问我：

> "如果装了 Photoshop，生成的 PSD 能编辑吗？**不要那种一个图层的文件**。"

我手上这台机器**没装 Photoshop**（只有 Creative Cloud 的辅助组件）。按常规思路，这个需求到此为止——"没装 PS，做不了"。

但仔细想，PSD 是一个**文件格式**，不是 Photoshop 的功能。就像 PDF 不需要 Acrobat 才能生成、DOCX 不需要 Word 才能生成。问题只是：谁来按格式规范把字节写出来。

于是我用 Python 直接写了一个分层 PSD：四个版面，每个版面把**每一块文字、每一张图**都做成独立图层，300dpi，带中文图层名，元素层带透明蒙版——在 Photoshop 里能自由移动、隐藏、替换，且移动时不会拖走背景。

代价是**五轮返工**。下面按踩坑顺序讲，每个坑给现象、根因、修复代码。

---

## 坑一：写盘成功、体积正常，图层却全是空白

### 现象

第一版用 `pytoshop` 写 PSD：

```python
psd.write(open('out.psd', 'wb'))     # 无异常
# 文件 30.5 MB —— 看起来非常正常
```

但读回来一验：**所有图层像素近零**（RGB 均值 0.6，alpha 均值 1，本该是 140+ 和 255）。

更迷惑的是，换个通道传法就直接崩：

```
OverflowError: Python integer -1 out of bounds for uint8
```

### 根因

`pytoshop` 1.2.1 对 **RGBA（带 -1 透明通道）** 的通道编码有缺陷：
通道字典 `{0,1,2,-1}` 能通过它的尺寸校验、能写盘，但写出的通道数据是空的；
传 `(H,W,C)` 数组或 list 则触发上面的溢出错误。

**"体积正常"是最大的陷阱**——30MB 来自通道长度声明，不代表里面有真实数据。
如果我只验证"写盘成功 + 文件大小合理"，就会交付一包空壳。

### 修复

换用 **`psd-tools` 的构建 API**（写入和读取同一套库，可控可验）：

```python
from psd_tools import PSDImage
from psd_tools.api.layers import PixelLayer

psd = PSDImage.new(mode='RGB', size=(W, H), depth=8)
psd.append(PixelLayer.frompil(pil_img, psd, name='01_txt_title', top=T, left=L))
psd.save('out.psd')
```

**教训**：生成类任务的验收标准不是"工具返回成功"，而是**把产物读回来做一遍等价性比对**。

## 坑二：目标 300dpi，出来只有一半

### 现象

面板宽 150mm，300dpi 应为 **1772×2835** 像素；实得 **886×1417**——正好一半。

而**同一份 HTML 打印出来的 PDF 尺寸完全正常**。这个对比极具误导性：很容易判断成"截图工具不行"。

### 根因

源稿里有一行为屏幕预览写的样式：

```css
@media screen { .poster { transform: scale(0.5); } }
```

截图走的是**屏幕**媒体，被缩掉一半；**打印媒体不生效**，所以 PDF 是对的。
一份文件，两条渲染路径，结论完全不同。

### 修复

截图前注入覆盖样式，并且**断言画布尺寸**——不满足就报错退出，绝不"默默出图"：

```python
page.add_style_tag(content='@media screen{.poster{transform:none !important}}')
# 之后断言：abs(实测宽 - 目标宽) > 6  →  报错退出
```

**教训**：同一份源稿在不同渲染媒体下可能差一倍。**任何尺寸都要断言，不要相信"看起来对"**。

## 坑三：元素与底图差 1~3 像素

### 现象

把每个文字块单独抠成图层后，它与底图之间出现 0.15% 的比例差——在版面远端累积成 1~3px 错位，高对比边缘处单像素差最大 **248**。

看起来像"内容错了"，其实是"网格错了"。

### 根因

我给截图设的缩放是 `device_scale_factor = 300/96 = 3.125`（名义值）。
但**截图输出像素会取整**：实测 1769px ÷ 566.92 CSS px = **3.1204**。

用名义值定位元素，误差必然随坐标放大。

### 修复

以**整幅底图的实际像素尺寸**反推比例，并用它作为画布尺寸与定位基准：

```python
W, H = base_im.size                        # 实测画布
kx, ky = W / panel_css_w, H / panel_css_h  # 实测比例（禁用名义 3.125）
L, T = round(css_x * kx), round(css_y * ky)
```

更进一步：**所有图层都在同一张整幅栅格上裁剪**（而不是各自按元素矩形单独截图），
这样每层的像素网格天然一致，从根上消灭独立取整带来的漂移。

## 坑四：图层一移动，就把背景一起拖走

### 现象

逐元素单独截图得到的图层，**带着一块底层背景**。在 Photoshop 里一拖动，
文字后面跟着一块"背景补丁"——分层等于白做。

### 修复（以及一个反直觉的参数）

用"同位置与底图**逐像素求差**"来生成透明蒙版：只有该元素真正画上去的墨迹保留，其余全透明。

```python
ink  = (np.abs(isolate_render - base_rgb).max(axis=2) > 20)   # 阈值 20
rgba = np.dstack([isolate_render.astype(np.uint8), (ink * 255).astype(np.uint8)])
```

这里**我犯过一次方向性错误**：最初把阈值设成 3，想"尽量保留细节"，结果**偏差反而从 7500 像素涨到 12030 像素**。

原因很反直觉：**隐藏/显示相邻元素会让整页渲染产生 3~4 级的微差**（合成取整、阴影抖动）。
阈值太低，这些微差就被误判成"墨迹"，于是某一层以**底色**盖住了下层的**真实内容**——
不是漏了东西，是多了块假的。

**真实内容与背景的差通常在 40~100 级，渲染微差只有 3~4 级**，所以阈值取 20 左右刚好把两者分开。

另外，裁剪框要取**墨迹自身的包围盒**，不能按元素 CSS 矩形换算——超出画布的元素会算出负宽，整层丢失。

## 坑五：中文图层名与 300dpi 元数据

两个小坑，但都会让产物"看着能用、打开就废"。

**中文图层名崩溃**：

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 0-1
```

PSD 图层记录的 legacy 名称是 pascal 字符串，库默认按 **MacRoman** 写。
解法是双名：**ASCII 名 + luni（Unicode 图层名）块**存中文，Photoshop 优先显示后者。

```python
lay = PixelLayer.frompil(im, psd, name='05_txt_ring-center')  # ASCII，必须
lay.tagged_blocks['luni'] = '环形中心·制造运营管理'            # 中文，PS 里显示这个
```

**分辨率元数据**：不写这个资源，PSD 会按 72dpi 打开——1772×2835px 显示成 62×100cm，印刷尺寸全错。
它要按规范包成二进制资源块（16 字节、大端）：

```python
import struct
from psd_tools.constants import Resource
from psd_tools.psd.image_resources import ImageResource

res = struct.pack('>IHHIHH', 300 << 16, 1, 1, 300 << 16, 1, 1)
psd.image_resources[Resource.RESOLUTION_INFO] = ImageResource(
    signature=b'8BIM', key=1005, name='', data=res)
```

## 坑六（最值钱）：校验工具告诉我"层序反了"，我差点把对的改错

### 现象

图层写完了，我用库自带的合成函数验证：

```python
d.composite(force=True)
```

结果出现了**自相矛盾**的结论：

```
只显示 A 层 → 得到 A 的内容 ✓
只显示 B 层 → 得到 B 的内容 ✓
A、B 同时显示 → 显示的却是 A     ✗  （按文件层序，B 应该在 A 上面）
```

我据此判断"层序写反了"，准备把 append 顺序整个翻转。

**在动手之前我先做了一次独立复核**：自己写了三十行 alpha-over 合成器，按图层列表顺序逐层叠加。

结论反转——**文件是对的，是库的合成路径给了我误导**。
如果当时直接"修"了，就会把一个正确的文件改坏，而且改完还"验证通过"（因为错误判据一直在）。

### 根因

库的合成/缓存路径为通用场景优化，和文件语义不完全一致；
`layer.numpy()` / `layer.topil()` 这类便利函数在部分层上同样失真。

### 正确做法

**判据要自己实现**，库的便利函数只当参考：

```python
canvas = np.zeros((H, W, 4), float)
for l in psd:                       # 列表顺序 = 由底到顶
    src = np.array(l.topil()).astype(float)
    ...                             # 标准 alpha-over
diff = np.abs(canvas[..., :3].astype(int) - reference).mean()   # 与原稿比对
```

最终四联的还原误差：**两联 0.004 以下，一联 0.02，最差一联 0.05%**（集中在叠压照片接缝的 1px 细边）。

### 这条坑的普适版本

> **当工具断言你的产物错了，先写一个独立实现复核，再决定动不动手。**

自动化流水线里，"验证"本身也是代码，也会错。
一个错误的判据 + 一个听话的执行者 = 把正确的东西改成错的，然后盖章通过。

## 可带走的配方

**配方 1：生成类任务，验收 = 读回 + 等价比对**
不看"写盘成功"、不看"文件大小正常"——把产物读回来，和源做逐像素/逐项比对。

**配方 2：尺寸必断言**
每个中间产物都断言尺寸/数量（画布 1772px、图层数 19、图 17 张）。不满足就退出，别出图。

**配方 3：定位比例用实测反推**
任何"名义缩放系数"都可能被取整；用底图实际像素数 ÷ 设计尺寸得到真实比例。

**配方 4：透明蒙版阈值取在两类差异之间**
先量一遍"真实内容差"和"渲染噪声差"各是多少级（本例 40~100 vs 3~4），阈值取中间（20）。
阈值调低不等于保真，可能是在往产物里注入假内容。

**配方 5：给出可编辑的边界**
交付时明确写清"能改什么、不能改什么"——本例的分层 PSD 能移动/隐藏/替换/调透明度，
但文字是位图文字，**不能双击改字**（那需要 Photoshop 脚本建真文字层）。
把边界写在文档里，比让用户自己撞上去强。

## 三条铁律

1. **文件格式 ≠ 软件功能**——PSD/PDF/DOCX 都可以由程序按规范写出，机器上没有 Photoshop 不是理由。
2. **"成功返回 + 体积正常"不是验收**——生成类任务必须读回比对，静默写空的产物最危险。
3. **判据也要被验证**——工具说产物错了，先独立复核；否则你会把对的改成错的。
