# 用 Markdown 文件编排 AI 任务流：一个"反直觉"的协议设计（AI 枢纽实战·Ⅴ）

> 摘要（公众号摘要字段，≤120 字）：给 7 个异构 AI 编排任务，我放弃了一切"现代"方案——不用 API、不用消息队列、不用数据库。最后靠一堆 Markdown 文件搞定了。这篇讲这个"反直觉"设计的完整逻辑。

> 「AI 枢纽实战」系列·Ⅴ | 前几篇讲了这个系统怎么长出来。这一篇拆开它最核心的一层：任务协议——为什么是文件、文件里写什么、怎么用文件编排依赖与并发。

---

## 一、引子：所有"现代方案"都试过，然后我放弃了

给多个 AI 编排任务，第一反应当然是"上工具链"。我列过一串候选：

```
❌ 统一 API 集成：写适配层，调各家的 SDK/HTTP 接口
❌ 消息队列：任务发到队列，AI 消费者取
❌ 数据库：任务表 + 状态字段，SQL 驱动
❌ 工作流引擎：Airflow 那套 DAG
```

全部放弃了。原因只有一个词：**异构**。

我本机的 7 个 AI 工具，来自 7 个不同厂商，接口形态是这样的：

| 工具 | 无头调用方式 | 形态 |
|------|-------------|------|
| A | `cli run --format json -`（stdin 传提示词） | node 脚本 |
| B | `hermes -z "提示词"` | 独立 exe |
| C | `zcode.cjs --prompt "..." --json` | node 脚本 |
| D | `codex exec "..."` | node 脚本 |
| E | `pi -p "..."` | node 脚本 |
| F | `openclaw.mjs agent --local -m "..."` | 长驻网关 |
| G | `dsh --profile headless "..."` | node 脚本 |

**7 个工具 7 种调用方式**——写统一 API 适配层？那就是给每个厂商的每次升级都埋一颗雷。

那消息队列/数据库呢？它们解决的是"任务怎么流转"，但没解决**"AI 怎么读懂任务"**——你还得为每个 AI 定义输入输出格式，仍然是 N 份适配。

于是我停下来问了一个更根本的问题：

> **这些 AI 有什么是"共同会"的？**

答案很朴素：**它们都会读写文件**。

每一个 AI 编码工具，不论厂商、不论架构，都自带 `read`/`write`/`edit` 工具。文件系统是它们唯一无争议的公共接口。

**顿悟：这个系统的"总线"不应该是 API，应该是文件系统。**

## 二、协议设计（一）：任务卡解剖

既然是文件总线，第一件事是定义"任务"长什么样。答案是一张 Markdown 文件——**任务卡**。

```markdown
---
id: T-2026-0911-01          # 唯一编号（日期+序号，自动分配）
from: human                  # 来源
to: pi                       # 执行方（派给谁）
status: pending              # 状态（见下文状态机）
created: 2026-0911 12:50
priority: P1                 # 可选：优先级
depends_on:                  # 可选：依赖谁
  - T-2026-0911-00
context:                     # 上下文文件（让执行方先读）
  - ../handoff/H-latest.md
acceptance:                  # 验收标准
  - 产出结构化报告到 outputs/pi/
  - 回写 status=done 并填结果摘要
---

# 任务：<标题>

## 目标
## 背景
## 任务步骤
```

**设计要点**：

1. **frontmatter 是机器读的**（YAML），**正文是人/ AI 读的**——一份文件同时服务两类读者
2. **字段可选、缺省有默认**（没有 priority 就是 P2）——协议演进时不破坏旧卡
3. **`acceptance` 显式写出验收标准**——把"什么算完成"从执行方手里拿走

## 三、协议设计（二）：状态机与四落点

**状态机**是任务的骨架：

```
pending ──派发──> doing ──完成──> done
   ↑               │
   │               ├─ 失败 → 重试（回 pending，计数+1）
   │               ├─ 重试耗尽 → 改派（换执行方，回 pending）
   │               └─ 无候选 → blocked（等人）
   └────────────────┘
cancelled：人工取消
```

**四落点**是任务的验收契约——一次任务必须完成四件事才算"完成"：

| 落点 | 内容 | 为什么 |
|------|------|--------|
| ① 产出报告 | `outputs/<agent>/<日期-主题>/report.md` | 有交付物 |
| ② 任务卡回写 | status=done + 结果摘要 | 有状态 |
| ③ 交接单联动 | `handoff/H-latest.md` 追加记录 | 有上下文（下一个能接） |
| ④ 变更日志 | `PROGRESS.md` 追加一行 | 有历史（人能审计） |

**这四个落点的本质是把"完成"的定义权交给机器**——校验器检查"文件在不在、字段全不全"，不看 AI 说没说自己完成。

（实战验证：有 AI 两次自报 DONE 零产出，全靠这个机制拦下。）

## 四、编排机制：从"单任务"到"能编排"

有协议之后，编排就是"按协议驱动文件"。核心三件事：

**① 调度：发现 → 派发 → 验收**

```
每 30 秒：
  扫收件箱（一行字→转卡）
  → 找可执行的卡（状态过滤 + 依赖检查）
  → 按优先级排序
  → 派给对应执行方（调它的 CLI，让它读卡干活）
  → 校验四落点 → 通知
```

**② 依赖编排：用 `depends_on` 串流程**

```yaml
# B 卡声明依赖 A 卡
depends_on:
  - T-2026-0910-01
```

调度器行为：依赖没完成的卡自动跳过；**依赖完成后自动接续**（不需要人工触发）。实测一条 A→B 任务链全自动跑完。

**③ 并发防护：三重幂等**

自动化的第一个新问题就是并发——守护进程在跑，人又手动敲了命令，同一张卡被调度两次怎么办？

```
① 依赖过滤：不该跑的不跑
② done 跳过：跑完的不重跑
③ 派发锁：正在跑的不并发
```

第③层是"卡级锁"（`tasks/.dispatch-<id>.lock`，写持有者 PID）——还配了"持有进程存活检测"（进程死了锁自动清理，防死锁）。

**这层是被现实教育的**：有天守护进程和我手动命令同时拉起同一张卡，两个 AI 会话对着同一张卡抢着干活——当天补上锁。

## 五、协议演进：怎么加字段不破坏旧数据

协议用了两周之后要加工作流能力（优先级/重试/改派）。**怎么改协议不炸掉历史数据？**

答案：**新字段全部可选 + 缺省即旧行为**。

```yaml
priority: P1        # 没有 = P2（旧卡行为不变）
retry: 1            # 没有 = 0（不重试）
fallback:           # 没有 = 不改派
  - codex
```

**"缺省即旧行为"是协议演进的第一原则**——这样历史上几十张卡不用改一个字节。

还有一个隐藏的工程细节：解析器要**容忍未知字段**（别人加的字段不报错）——为未来留扩展位。

## 六、为什么文件协议赢了（对比一下）

| 维度 | API/消息队列/数据库 | 文件协议 |
|------|-------------------|---------|
| 适配成本 | N 个工具 N 份适配（还随升级失效） | 零适配（AI 天生会读写文件） |
| 可调试性 | 黑盒（看日志/抓包） | 打开文件就能看 |
| 可审计 | 要另建审计系统 | git 天然版本化、人可读 |
| 人工介入 | 要写工具/管理界面 | 直接用编辑器改 |
| 故障恢复 | 依赖系统可用性 | 文件在就一切都在 |
| 学习成本 | 要理解你的 API | 会 Markdown 就能参与 |

**一句话：文件协议的"低技术含量"恰恰是它最大的技术优势**——它把复杂度从"接口适配"转移到了"协议约定"，而后者是**一次性的、跨厂商通用的**。

## 七、可带走的配方

**配方 1：先找"最大公约数接口"**
设计多系统协作前，先问"它们共同会什么"——而不是"我想要什么接口"。找到公分母，协议就成功了 80%。

**配方 2：机器读的部分和人类读的部分分开**
frontmatter（机器）+ 正文（人类）——一份文件服务两类读者。

**配方 3：验收标准写进协议**
`acceptance` 字段让"完成"可校验，是自动化的地基。

**配方 4：新字段可选 + 缺省即旧行为**
协议演进不破坏历史数据的第一原则。

**配方 5：幂等至少三层**
依赖过滤 + 完成跳过 + 并发锁——不同原因的重复需要不同层次的防护。

---

## 三条铁律

1. **异构系统之间，最低技术含量的介质往往是最优介质**
2. **协议先于实现**——格式定死了，实现随便换
3. **"谁定义完成"决定系统能不能自动化**——定义权必须在机器校验手里
