# 从「能跑」到「能用」：2 天做出每天都在跑的 AI 协作系统（AI 枢纽实战·下）

> 摘要（公众号摘要字段，≤120 字）：POC 能跑不等于能用。MVP 两天补上调度、多执行方和通知，也被现实连打三次脸：AI 假完成、参数不认识、守护进程从未真正运行过。三次打脸，三条铁律。

> 「AI 枢纽实战」系列·下 | 上一篇的 POC 证明了"文件协议能驱动 AI 协作"。但 POC 能跑 ≠ 能用——这篇讲 MVP 阶段真实发生的事：三个关键增量、一次误报的教训、以及一个差点永久埋着的致命缺陷。

---

## 一、POC 的三个局限（为什么不能停在 POC）

POC 结束时，系统能跑通一张卡。但它有三个硬伤：

```
❌ 每张卡要手动跑一次命令（没有调度）——这不叫自动化，叫"省了复制粘贴"
❌ 只接了 1 个智能体——协作的价值在"多"，一个谈不上协作
❌ 跑完/跑挂都没有通知——得盯着看，人还是不能离场
```

所以 MVP 的标准很清晰：**让我能每天真的用它干活**。翻译成验收条件：

| MVP 验收条件 | 对应增量 |
|-------------|---------|
| 投一张卡就不用管了 | ① 调度器（daemon） |
| 多个智能体都能干活 | ② 适配器模板化 |
| 干完/干挂我都知道 | ③ 通知体系 |

**红线**（MVP 阶段坚决不做的）：归档体系、记忆同步、MCP、工作流依赖、各种增强——**这些全是"以后"，不是"最小可用"**。

---

## 二、增量一：调度器——把"手动"变"自动"

核心是一个常驻进程（daemon），30 秒一轮：

```
每 30s：
  扫收件箱 → 转成标准任务卡
  → 找可执行的卡 → 交给对应智能体的适配器
  → 校验四落点 → 通知结果
```

看起来简单，但"自动"立刻带来新问题——**并发**：daemon 在跑，我又手动敲了命令，同一张卡被调度两次怎么办？

解决方案是"三重幂等"：

```
① 依赖过滤：依赖的卡没完成，不跑
② done 跳过：已经完成的卡，不重跑
③ 派发锁：正在跑的卡，不并发（卡级锁文件 + PID 存活检测）
```

**一个真实教训**：这三层不是一次设计出来的。是"手动 + daemon 并发拉起同一张卡、两个智能体同时干活"真实发生后才补的（那天两个 pi 会话对着同一张卡抢着写报告）。**并发问题只有真的并发过才知道疼。**

## 三、增量二：适配器模板化——从 1 个到 7 个的成本控制

MVP 要接多个智能体。如果每个都从零写，成本会失控。于是我抽了一个基类（base.py），让每个适配器只剩两个字段：

```python
class PiAdapter(BaseAdapter):
    NAME = "pi"                                    # 执行方名

    def build_command(self, prompt):               # 就这一个方法
        return resolve_node_script("pi", PI_JS) + ["-p", prompt]
```

**效果：实测 576 行 → 154 行（-73%）**，新执行方接入从"半天"压到"30 分钟"。

模板化过程里还顺手统一了三件"每次都忘"的事：

| 统一项 | 内容 |
|--------|------|
| **CLI 直调真身** | 所有适配器都先解析出真实可执行路径（node+js / exe），永不直接跑 `.CMD` |
| **启动前探测** | 调执行方前先探测可用性，失败快速失败 + 人话诊断（而不是抛个谜语） |
| **统一 CLI 接口** | 全部支持 `--list/--task-id/--context-file`（这是被坑出来的，见下文） |

## 四、增量三：通知——让失败也可见

跑完有通知很容易想到；**跑挂也有通知**才是关键。（毕竟没通知的失败 = 静默失败 = 你还得盯着。）

实现上是"双通道并行"：钉钉单聊 + 飞书群，任一成功即送达。三类消息：

- ✅ 任务完成（含结论摘要 + 报告路径）
- ⚠️ 失败重试中
- 🔴 失败置 blocked（需要人介入）

## 五、MVP 阶段的三次"打脸"（最有价值的部分）

### 打脸一：hermes 的"假完成"

有个智能体（hermes）两次自报 DONE，但**零产出**——没有报告、没有回写。它"礼貌地"总结了一段话就结束了。

**靠什么发现的？** POC 阶段定的四落点校验。校验器一跑：报告不存在 → 判定失败。

**教训**：永远不要相信 AI 说"我完成了"。完成的定义权必须交给机器校验。（POC 埋的伏笔在这里回收了。）

### 打脸二：调度器传错参数，5 个执行方"假装在干活"

调度器调用适配器时统一传了一个 `--context-file` 参数。跑了几天才发现：**有 5 个适配器的命令行根本不认识这个参数**——它们每次被调用都在报"未知参数"直接退出。

（因为当时很多任务是手动直调适配器完成的，掩盖了这个缺陷。）

**修复**：统一 CLI 接口 + 加了一条"接口一致性测试"——每个适配器必须能接受调度器的标准参数，锁死这个坑。

**教训**：**测试要锁"接口契约"，不只是"功能正确"**。

### 打脸三（最狠）：守护进程从未真正运行过

这个值得完整讲：

系统里有"daemon 每日自维护"的记载，记录显示曾"实测通过"。直到某天让一个新接入的智能体做自检——它发现：

> **hub.py 缺少 `if __name__ == '__main__': main()` 这一行入口。**

这意味着什么？**所有 `python hub.py --xxx` 命令都是静默空转**——exit 0、零输出、什么都没干。而 daemon 就是靠 `python hub.py --daemon` 启动的——**它从未真正运行过**。

那之前的"实测通过"是怎么来的？是任务其实由手动直调适配器完成了，**掩盖了缺陷**，然后记录里写了一句想当然的"daemon 实测通过"。

**修复**很简单（补一行入口）。但教训很贵：

1. **import 式测试不暴露入口缺失**——必须有"子进程直跑有输出"的冒烟测试
2. **"实测通过"的记录必须附证据**（PID 在哪？输出在哪？）——连人类写的记录都可能与事实不符
3. **让新成员/新智能体做自检**——它没有历史包袱，能发现老成员的盲区

## 六、MVP 验收：用数字说话

```
✅ 执行方：5 个 L2 全自动（opencode/hermes/deepseek/zcode/codex）
✅ 调度：daemon 30s 周期 + 三重幂等
✅ 通知：双通道（钉钉 + 飞书），任务完成/失败全推送
✅ 验收：四落点机械化校验（拦下过假完成）
✅ 测试：40+ 单测（含接口一致性、CLI 入口冒烟）
✅ 实战：几十张真实任务卡闭环，零信息丢失
```

**MVP 的正确终点**：不是"功能齐全"，而是"**每天真的在用，且能自己发现自己的问题**"。

---

## 七、POC → MVP 的三个跨越（可带走）

**1. 不要停在"能演示"，要跨到"能离场"**
POC 的验收是"假设成立"，MVP 的验收是"投完不用管"。判据：**你能不能去干别的，回来看结果就行**。

**2. 成本控制靠"模板化"，不靠"堆人力"**
从 1 个执行方到 7 个，靠的是基类 + 30 分钟接入，不是每个重写一遍。**规模化之前先抽象。**

**3. 让失败可见 = 让系统可托付**
完成通知 + 失败通知 + 巡检告警，一个都不能少。**静默的失败比失败本身更危险。**
