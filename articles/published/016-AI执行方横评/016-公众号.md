# 7 个 AI 执行方横评：谁适合当"自动化流水线"上的工人？（AI 工具实测·上）

> 摘要（公众号摘要字段，≤120 字）：评测 AI 工具通常比"谁更聪明"。但如果你要把它们接进自动化流水线，标准完全不同：能不能无头调用、接入要多久、稳不稳。这篇是一次真实的"执行方选型"复盘。

> 「AI 工具实测」系列·上 | 目标不是评选"最强 AI"，而是回答一个工程问题：手里这些 AI 编码工具，哪些能在无人值守的流水线上干活？

---

## 一、引子：换一把尺子

市面上的 AI 工具评测，比的通常是"谁更聪明"——写代码能力、推理能力、上下文长度。

但当你要把它们**接进自动化流水线**（无人值守、程序化调度）时，关心的完全是另一组问题：

- **能不能无头调用**？（没有图形界面，程序直接调得动吗）
- **怎么调**？（调用姿势是什么，要传什么参数）
- **接一个要多久**？（工程成本）
- **稳不稳**？（用一周会不会自己坏）

这篇就是拿这把"工程尺"量的：**本机 7 个 AI 编码工具的真实接入复盘**。

---

## 二、评测框架（4 个维度）

| 维度 | 问题 | 为什么关键 |
|------|------|-----------|
| **① 可无头** | 有没有非交互模式？ | 一票否决项——没有它，一切免谈 |
| **② 调用姿势** | 命令行怎么调？参数形态？ | 决定适配器怎么写 |
| **③ 接入成本** | 从零到跑通要多久？ | 决定规模化可行性 |
| **④ 稳定性** | 跑一周会不会坏？ | 决定能不能无人值守 |

**先给结论**：7 个全部接入了自动化流水线，**平均接入时间约 30 分钟/个**（靠一个统一的适配器模板收敛的）。下面是逐个明细。

---

## 三、逐个评测

### 1. OpenCode —— "标准化最好"

```
调用姿势：opencode run --format json -     （- 表示从标准输入读提示词）
形态：原生 .exe
```

**亮点**：原生可执行文件 + 官方 `run` 子命令 + `--format json` 结构化输出——**开箱即用的自动化友好**。

**一个细节**：它支持从**标准输入**读提示词（`-`）——这解决了一个隐蔽的坑：**Windows 命令行长度限制**（约 32K 字符）。长提示词走 stdin 就完全绕开了。这是 7 个里唯一原生支持 stdin 的。

**接入耗时**：~20 分钟。**稳定性**：好。

### 2. Hermes —— "老老实实的独立 exe"

```
调用姿势：hermes -z "提示词"
形态：独立 .exe（不在 PATH 时要写绝对路径）
```

**亮点**：`-z` 参数一把梭，简单直接。

**小坑**：安装位置特殊（虚拟环境里），`which` 找不到时要配 fallback 绝对路径。

**接入耗时**：~25 分钟。**稳定性**：中（曾观察到长任务下"自报完成但零产出"——靠验收机制兜住了）。

### 3. ZCode —— "参数最全但字段最讲究"

```
调用姿势：zcode.cjs --prompt "..." --cwd <目录> --mode yolo --json
形态：node 脚本
```

**亮点**：参数丰富——能指定工作目录、运行模式、JSON 输出。

**坑**：配置文件的**格式有讲究**（某个字段从"对象"改成"字符串"才对——格式不对直接拒启动）。工具升级后配置格式变了，旧配置会失效。

**接入耗时**：~40 分钟（含排查配置格式）。**稳定性**：好。

### 4. Codex —— "沙箱参数是重头戏"

```
调用姿势：codex exec --skip-git-repo-check --sandbox workspace-write \
         -c 'windows.sandbox="unelevated"' -C <目录> "提示词"
形态：node 脚本
```

**亮点**：`exec` 单发模式干净利落。

**坑（最多）**：
- 沙箱模式参数必须显式传对（某个默认值会导致启动失败）
- **配置会被第三方工具静默重置**（一个多工具管理软件会"顺手改"它的配置）→ 后来干脆在命令行里显式传参覆盖配置

**接入耗时**：~1 小时（主要花在沙箱排查）。**稳定性**：中（配置漂移风险）。

### 5. pi —— "最轻量的一个"

```
调用姿势：pi -p "提示词"
形态：node 脚本
```

**亮点**：极简——`-p`（print 模式，非交互）一个参数，输出干净。

**坑**：模型/凭据配置（provider 的 key 要配好，key 失效时会"全任务失败"——看起来像工具坏了，其实是环境问题）。

**接入耗时**：~25 分钟。**稳定性**：好（前提是凭据有效）。

### 6. AutoClaw（OpenClaw）—— "唯一的长驻型"

```
调用姿势：openclaw.mjs agent --local --agent main -m "提示词"
形态：node + 长驻网关架构
```

**亮点**：功能最重（多渠道网关 + 多智能体 + 工具链），`--local` 模式可以绕过它的常驻网关直接干活。

**坑**：
- 需要显式设置环境变量指向它的状态目录（否则找不到配置）
- 它的文件工具**沙箱锁定在自己的工作区**——跨盘操作要走内部 shell

**接入耗时**：~1 小时。**稳定性**：好。

### 7. DeepSeek Harness（dsh）—— "配置最娇贵"

```
调用姿势：dsh --profile headless "提示词"
形态：node 脚本
```

**亮点**：`headless` 档专为"答完即退"设计，语义清晰。

**坑（最娇贵）**：
- **每次启动都重写自己的配置文件**——所以在"受限沙箱环境"里会直接起不来（配置不可写）
- 默认模型配置漂移过一次（指向一个不存在的 provider，直接拒启动）

**接入耗时**：~1 小时（含两轮排查）。**稳定性**：中。

## 四、横向对比表

| 执行方 | 可无头 | 调用姿势 | 接入耗时 | 稳定性 | 特殊处理 |
|--------|:---:|---------|:---:|:---:|---------|
| OpenCode | ✅ | `run --format json -`（stdin） | 20 min | 好 | 唯一支持 stdin（绕长度限制） |
| Hermes | ✅ | `-z "..."` | 25 min | 中 | 需要 fallback 路径 |
| ZCode | ✅ | `--prompt ... --json` | 40 min | 好 | 配置格式讲究 |
| Codex | ✅ | `exec --sandbox ... "..."` | 60 min | 中 | 沙箱参数 + 防配置被改 |
| pi | ✅ | `-p "..."` | 25 min | 好 | provider key 维护 |
| AutoClaw | ✅ | `agent --local -m "..."` | 60 min | 好 | env 变量 + 工作区沙箱 |
| dsh | ✅ | `--profile headless "..."` | 60 min | 中 | 配置每次重写（限环境） |

**平均接入：~35 分钟/个**（7 个全部接完）。

## 五、选型建议（什么场景选什么）

**① 要"最省事"** → OpenCode（原生 exe + stdin + JSON 输出，自动化友好度第一）

**② 要"最轻量"** → pi（一个参数，输出干净）

**③ 要"功能最全"** → AutoClaw（但接入成本最高）

**④ 要"参数精细控制"** → ZCode（工作目录/模式可指定）

**⑤ 有企业网关约束** → Codex（但注意沙箱与配置漂移）

**⑥ 主动避开**：任何"每次都重写自己配置"或"依赖图形界面"的工具（前者在受限环境会挂，后者根本进不来）。

### 一个最重要的筛选标准

> **"可无头"是唯一的一票否决项**——GUI 工具再强，进不了流水线。

## 六、可带走的接入清单

接一个 AI 工具进自动化流水线，标准动作：

```
1. 确认无头模式（找 -p/--print/exec/run 类参数）
2. 拿到非交互调用命令（并验证 stdout 有结果）
3. 解析真实入口路径（node+js 或 exe 绝对路径，绕开包装脚本）
4. 写一个 25 行的适配器（统一模板：NAME + build_command）
5. 自检：投一张卡 → 跑通 → 验收四落点
6. 沉入巡检清单（每天检查入口是否还在）
```

**第 4 步的"25 行"怎么做到的？**——靠一个抽出共同逻辑的基类，把"每个工具的差异"压缩成一个人写的 `build_command` 方法。这是规模化接 7 个的关键（下一篇会提到 GUI 工具的特殊情况）。

---

## 三条铁律

1. **选执行方看"可无头"，不是看"能力强"**
2. **接入成本靠模板化收敛，不靠"每个重写"**
3. **工具的"配置娇贵度"决定运维成本**——越爱自我改写的，越要防
