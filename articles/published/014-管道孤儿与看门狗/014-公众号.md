# 管道、孤儿与看门狗：一次"通知迟到 8 分钟"的事故调查（自动化硬核·Ⅱ）

> 摘要（公众号摘要字段，≤120 字）：任务完成了，完成通知却迟到 8 分钟；期间调度进程一动不动。顺着进程树追下去，揪出了三个"孤儿"和一条攥着不放的管道。这是一次完整的故障侦探记。

> 「自动化硬核」系列·Ⅱ | 上一篇讲三个陷阱时，第三个（管道阻塞）只给了结论。这一篇把事故调查过程完整还原——它比结论更值钱，因为"怎么查"比"怎么修"更通用。

---

## 一、案发：通知迟到了 8 分钟

那天我在测试一条自动化链路：手机发一条消息 → 系统自动执行任务 → 完成后通知回到手机。

时间线（后来从记录里还原的）：

```
11:28:01  手机收到"已收到任务"回执          ← 一切正常
11:36     任务实际完成（产出文件都写好了）    ← 工作本身没问题
11:44:20  手机才收到"任务完成"通知          ← 迟到了 8 分钟
```

8 分钟对一个自动化系统来说很反常——正常应该"完成即通知"。

而且有个诡异的细节：**这 8 分钟里，整个调度进程像死了一样**——不处理任何新任务、不发任何通知。

**第一个判断：调度进程卡住了。** 那么问题来了——卡在哪？

---

## 二、线索一：一把没释放的锁

第一步查"系统账本"。调度系统给每张进行中的任务卡都有一把"锁文件"（内容是持有者的进程号），正常情况任务结束就释放。

检查：

```
派发锁：.dispatch-T-2026-0911-01.lock  ← 还在！（没释放）
内容：pid=26064
锁龄：15.1 分钟前创建
```

**两条信息**：

1. 锁没释放 → 说明"释放锁"的代码没执行到（正常逻辑里它在 `finally`，异常也会执行）
2. 锁的主人还在（pid 26064 是调度进程）→ 进程没崩，是**卡着**的

如果进程卡死了，会卡在哪？

---

## 三、线索二：进程树里的"三个孤儿"

查调度进程的子进程树：

```
26064  pythonw hub.py --daemon          ← 调度进程（卡着）
  └── 2860  python adapters/xxx.py --task-id T-2026-0911-01   ← 适配器进程（也卡着）
        └── （opencode 进程已退出）
24652  python hub_mcp_server.py          ← 孤儿 1
25720  python hub_mcp_server.py          ← 孤儿 2
26332  python hub_mcp_server.py          ← 孤儿 3
```

**疑点立刻出现**：那三个 `hub_mcp_server` 是谁的孩子？——看父进程号，它们的父亲**已经不存在了**。

这是典型的**孤儿进程**。

**推理链**：执行方（opencode）在工作时启动了几个"助手服务"（MCP server）。任务完成后 **opencode 主进程退出了，但它启动的助手服务没被回收**——它们变成孤儿，继续活着。

而据时间戳，最早的两个孤儿是**更早一次会话**留下的（存活了好几天）。

---

## 四、线索三：为什么"卡住"？（还原因果链）

关键问题：孤儿进程和"调度卡住"有什么关系？

看适配器进程（2860）的工作方式：它调用 opencode 时，用了**管道**捕获输出（`capture_output=True`）——这是"等着读它的输出"的标准姿势。

管道的规则是：

> **父进程要读到'输出结束（EOF）'，必须等所有持有管道'写端'的进程都关闭它。**

而 opencode 启动的助手服务（MCP server）**继承了 opencode 的 stdout**——也就是说，**它们是那条管道的另一个写端持有者**。

于是因果链闭环了：

```
适配器用管道读 opencode 的输出
    → opencode 完成任务后退出
        → 但它启动的助手服务成了孤儿，仍持有管道写端
            → 适配器读不到 EOF，一直等
                → 调度进程等适配器，一起卡
                    → 通知发不出去，任务卡在"进行中"状态
```

**"任务完成"是真的——只是完成信号被一条攥在孤儿手里的管道拦住了。**

---

## 五、验证：杀掉孤儿，一切瞬间恢复

推断必须验证。我从"最下游"开始清理：

```
杀掉卡住的适配器（2860）
    → 8 秒后：调度进程继续执行 → 完成通知发出（11:44:20）✓
    → 派发锁释放 ✓
    → 系统恢复正常 ✓
```

再杀掉三个孤儿助手服务——它们没有任何存在的理由了。

**案情确认**：孤儿进程 + 管道继承 = 整个调度链被一条永不关闭的管道拖住。

## 六、修复：四层防御（缺一不可）

修一个 bug 要四层防御？因为每一层防的是不同环节：

### 第一层：给孤儿问题"治本"——看门狗

自研的常驻助手服务（MCP server）必须能感知"主人没了"，然后自己退出：

```python
import os, threading, time, ctypes

def process_alive(pid):
    """Windows 进程存活检测"""
    SYNCHRONIZE = 0x00100000
    h = ctypes.windll.kernel32.OpenProcess(SYNCHRONIZE, False, pid)
    if h:
        ctypes.windll.kernel32.CloseHandle(h)
        return True
    return False

def watchdog():
    """父进程消失 → 自己退出（防孤儿）"""
    ppid = os.getppid()
    while True:
        time.sleep(10)
        if not process_alive(ppid):
            os._exit(0)

threading.Thread(target=watchdog, daemon=True).start()
```

**核心：每个可能被"遗弃"的常驻子进程，都要自带看门狗。**

### 第二层：给调度链"换管子"——临时文件

调度层不用管道捕获输出，改用临时文件：

```python
import tempfile
with tempfile.TemporaryFile(mode="w+", encoding="utf-8", errors="replace") as out_f:
    r = subprocess.run(cmd, stdout=out_f, stderr=out_f, timeout=TIMEOUT)
    out_f.seek(0)
    stdout = out_f.read()
```

**原理**：`wait` 只等目标进程本身退出——孤儿进程持有"文件句柄"完全不影响（不是"必须大家都关门"的管道语义）。

### 第三层：给全局"兜个底"——超时

调度进程调用适配器的命令加超时（比内层稍长，作为最后一道保险）：

```python
subprocess.run([...adapter...], timeout=3700)
```

**即使前两层都失效，超时也能让系统"最多卡这么久"。**

### 第四层：给锁"容错"——持有者存活检测

锁的获取逻辑升级：**如果锁的持有进程已经死了，立即清理这个残留锁**（那些"死进程留下的锁"会永久阻塞任务）。

```python
if lock.exists():
    pid = parse_pid(lock)
    if not process_alive(pid):
        lock.unlink()   # 死进程的锁可抢占
```

## 七、回到本质：为什么这个 bug 只有"实测"能发现

修复之后复盘最重要的一点：**这个 bug 逃过了 108 个单元测试。**

为什么？

- 单元测试测的是**逻辑正确**（函数输入输出对不对）
- 这个 bug 是**进程行为**（孤儿是否退出、管道是否关闭）——测试环境里模拟不出"子进程比父进程活得久"的真实场景

**它只能通过"真实使用"暴露**——一个真实的执行方（带真实的助手服务）+ 一次真实的长时间运行 + 一个真实的观察者（发现通知迟到）。

这引出自动化系统的一条元规律：

> **测试保的是"逻辑正确"，巡检验的是"状态健康"，而实测发现的是"行为异常"。三层缺一不可。**

---

## 八、可带走的配方

**配方 1：常驻子进程必须带看门狗**
任何"可能被遗弃"的子进程，都要能检测"父进程消失"并自行退出。

**配方 2：调用可能 spawn 子进程的 CLI，用临时文件而非管道**
管道有"所有写端关闭才算结束"的语义——孤儿会把它攥住。

**配方 3：超时兜底不可省**
哪怕前面两层都做了，也要有"最多卡 N 分钟"的保险。

**配方 4：锁要能识别"死持有者"**
死进程留下的锁 = 永久阻塞。锁的获取逻辑必须含"持有者存活检测"。

**配方 5：进程树是你最好的调试工具**
出问题时第一件事：看进程树（谁在跑、谁是谁的孩子、谁的爹没了）。

---

## 三条铁律

1. **孤儿进程有两种危害：泄漏资源，和攥住管道**
2. **管道是"共享写端"语义——有一个不关，读端就等不到头**
3. **进程行为类 bug，单测测不出，只有实测能抓**

---

如果你有常驻进程类的自动化，去检查两件事：①有没有"会活到父进程之后"的子进程？给它加看门狗。②输出还在用管道捕获吗？换成临时文件。
